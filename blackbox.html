THE CASE STUDY / 01

The challenge

Embedded firmware crashes often leave developers with raw addresses, stack traces, and low-level context that take time to interpret. BlackBox explores how a structured crash-ingestion pipeline can turn that information into a clearer diagnostic report.

My approach

I built a full stack workflow connecting a FastAPI service, persistent data storage, asynchronous processing, and a web dashboard. Crash information is ingested, linked to devices, processed, and presented with symbolized context and AI-assisted explanations.

Key features

  • REST endpoints for authentication, device management, crash submission, and knowledge-base documents.
  • Asynchronous background tasks using Celery and Redis for processing work outside the request cycle.
  • ELF/MAP-aware symbolization to connect raw addresses with more meaningful firmware context.
  • Retrieval-grounded diagnosis workflow that uses available knowledge-base material as context.
  • Containerized local setup and deployment of the web application and backend services.

Engineering decisions

I focused on separating API requests from longer-running analysis work, keeping diagnostic information structured, and making results readable from the dashboard. The project combines backend design, infrastructure, and an AI-assisted workflow rather than relying on a model response alone.

What I learned

This project strengthened my experience with multi-service systems, background workers, database-backed APIs, Docker, and production deployment.
